For tblUsers, we start with userId. With userId, we are making this field our primary key as we can use this value to identify users who have the same display names. This field will be provided by the application, and it cannot be null. For the creation of the primary key, it will be an auto increment value handled by the database. For tblMovies, we are using movieId. This is our primary key field that can not be null, and it will be handled by the backend application for passing the value. In terms of creation of the row, it will be handled by the database as it will be an auto increment value. In tblRatings we have two foreign keys: userId and movieId. For userId, the source table is tblUsers. We are doing an ON DELETE CASCADE for this, as when a user wants to be removed from the system, their associated ratings should be deleted as well. With movieId we are doing ON DELETE RESTRICT, since if a movie were to be accidentally deleted from the primary table it could cause all the ratings to be deleted as well. These will both be handled on the database level as it deals with records being deleted. For tblGenres, we are using genreId as our primary key. genreId can not be null, and it will be an auto increment value. Meaning we will be handling this on the database side when we are creating new genres. In tblMovieGenres, we have two FK fields. movieId and genreId. For movieId, this field can not be null as we do not want a blank value to have a genre. It will have ON DELETE CASCADE because if we were to delete the movie from the primary source table we should also delete the associated one in the junction table as we do not want orphan records. Now for genre ID, we are using not null and ON DELETE RESTRICT. The reason we are using ON DELETE RESTRICT is because multiple movies use these genres, so if action were used it could mess with multiple records. Overall, when it came down to the design choices I made when constructing this. I chose to do not null for most fields and all primary keys to be auto incrementing int values. When creating the fields, I do not want a default value to be passed from the backend if the user tries to submit a null value. Either it will be handled on the database end or it has to be required at the application level.

I think something a different designer would do when looking at this layout is that they would use an email ID as the primary key in the tblUsers table. The reason that I used that field is that I feel that emails as the primary key is not as clean as using an int value as a primary key. And if this application was a production application, it could be processing millions of records. So, passing int values between the backend and the database is much faster with such a small value compared to a varchar(150) value. Another design choice that people would do differently would be the size I have chosen for each varchar. I chose these specific sizes because I felt that, for the time being, that it would be a good enough size. The designer would choose the maximum size first. I feel that with the maximum size it is not needed as genre names, movie names, usernames are not that long, and we do not want very long usernames. As this would be much slower than something less than varchar(150).
